# Documentation Standard vNext

RF-ADR-009 section 5 retires `/docs` into GitHub Pages per repository, built
from hand-written sources in `pages/`. A scaffolded connector package follows
that contract directly — there is no separate documentation-readiness layer
inside the connector scaffold.

## Source and generated artifacts

`mkdocs.yml` sets `docs_dir: pages` and is the exact page-selection authority:
Material theme, `strict: true`, and a `nav` naming every page under `pages/`
(`index.md`, `installation.md`, `usage.md`, `deployment.md`, `concepts.md`).
The GitHub Pages workflow (`.github/workflows/pages.yml`) builds
`mkdocs build --strict --site-dir site` and deploys it — mirroring
`agent-connector-sdk`'s own Pages workflow verbatim, so switching every
repository to the shared `Knuckles-Team/pipelines` Pages workflow later is a
one-line change once that workflow accepts a configurable `docs_dir`.

## What a scaffolded package does *not* generate

The previous (pre-retarget) documentation standard described a bounded
agent-discovery delivery layer on top of the semantic layer: `docs/agent-readiness.json`,
`llms.txt` / `llms-sections/*/llms.txt`, `markdown-mirror-manifest.json`,
`agent-readiness-manifest.json`, and `.well-known/{api-catalog,mcp-server-card.json,agent-skills.json}`,
generated by `scripts/generate_agent_readiness.py` and checked by
`scripts/agent_readiness_tck.py`. That apparatus was tied to the AU-hosted
documentation and capability-discovery model and is **out of scope for the
SDK-based connector scaffold** (RF-ADR-009 does not require it, and connector
content discovery is now the native-MCP-primitives path — `tools/list`,
`skill://`, `prompts/list`, `ontology://`, `shapes://`, `manifest://connector`
— described in `PARITY_MANIFEST.md`, not a documentation-site artifact).

`scripts/agent_readiness.py` and `scripts/agent_readiness_tck.py` remain in
this skill's own `scripts/` directory as standalone tools (repository-manager
uses them directly, and they carry their own test coverage in
`tests/test_agent_readiness*.py`), but `scaffold_package.py` no longer copies
or wires them into a generated package. A repository that still wants that
delivery layer can adopt it separately; it is not part of what
`agent-package-builder` produces.

## Content discovery is the native MCP primitive path

For a connector generated by this skill, "what can an agent discover about
this package" is answered by the MCP server itself, not a documentation
artifact:

| Content | Discovered via |
|---|---|
| Tools | `tools/list` |
| Skills | `skill://<name>/SKILL.md` (fastmcp's skills provider) |
| Prompts | `prompts/list` / `prompts/get` |
| Ontology / SHACL shapes | `ontology://<connector>/<file>.ttl`, `shapes://<connector>/<file>.ttl` |
| The connector manifest (sync presets, identity, schema mappings) | `manifest://connector` |

epistemic-graph's pack importer reads the same listings a fleet gateway does
(RF-ADR-009 section 2.1) — there is exactly one channel, so a scaffolded
package cannot drift between "what it documents" and "what it serves."

## Access and privacy policy (unchanged)

Public documentation URLs use HTTPS and never contain credentials, queries,
private-network addresses, or private hostnames. `pages/` source Markdown
must not contain a secret-like assignment, a bearer value, a credential URL,
or a private endpoint — the same rule that governs every other generated
file (`PARITY_MANIFEST.md`'s current-only rejection gate).
